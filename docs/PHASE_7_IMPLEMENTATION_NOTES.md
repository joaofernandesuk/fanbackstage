# Phase 7 implementation notes

Private sessions use server-persisted participant state; browser timers never determine billable use. When any required creator/viewer participant disconnects, the session enters `reconnecting`, accumulated active seconds are frozen, and billing pauses immediately. All required participants must reconnect within the configurable 30-second default grace period before a new active interval can begin. Grace expiry ends the session and settlement uses only already accumulated billable seconds. Provider disconnect/reconnect events are idempotent.

For 2-to-1, one requesting viewer is the sole payer, one specifically identified eligible follower is invited through a bounded masked candidate list, and the creator's separate 2-to-1 rate is snapshotted. The second viewer must explicitly accept before the creator can accept, has a session/user-scoped short-lived token, and has no financial responsibility or access to the payment-attempt identifier. The session cannot activate or bill until creator, payer, invited viewer, and payment authorization are all present. There is one timer and one settlement; split-payer billing and implicit conversion to 1-to-1 are deferred.

Settlement rounds in integer minor units as `ceil(rate_minor * authoritative_seconds / 60)`, applies the stored minimum once, and never exceeds the stored authorization cap. Permanent tests cover 1, 30, 60, 61 and 95 second intervals, reconnect exclusion, replay-safe participant events, and idempotent final ledger settlement. A session that never reaches ACTIVE is cancelled without a minimum charge.

The LiveKit client receives only API-issued short-lived tokens. Private tokens are session- and user-scoped; uninvited users cannot obtain one. Public viewer tokens cannot publish. Public recording is an egress foundation only; private recording is disabled by design.

LiveKit JWT expiry limits initial/reconnect authority but does not disconnect an established client. FanBackstage therefore uses authenticated RoomService controls for terminal and revocation transitions: `DeleteRoom` for room/session end or creator suspension, and `RemoveParticipant` for bans or viewer authority loss. Signed join callbacks repeat the canonical PostgreSQL compliance/entitlement/ban decision so a cached self-hosted token cannot persistently recreate or rejoin a terminal/denied room; scheduled reconciliation retries provider failures.

Local real-stack validation uses a browser-reachable LiveKit signalling endpoint and a loopback-advertised, published UDP mux port. This avoids Docker bridge ICE candidates being offered to host Chromium. The E2E browser is granted camera/microphone permission and uses Chromium's fake-media device flags; it proves actual creator track publication and viewer subscription without provider or presence mocks.

Paid Live requests snapshot the creator-owned option label, price, currency, and acceptance requirement at submission. Provider confirmation precedes financial success. Acceptance-required requests enter `paid_pending_creator`; only creator acceptance creates the single immutable settlement and canonical `paid_request` event. Decline, expiry, and late capture create a durable refund requirement/liability through the existing excess-capture path and never settle creator revenue. Expiry is worker-driven and replay-safe.

Live reactions are a bounded enum and persist only room/type aggregate counts. They have a dedicated aggressive rate limit and do not create one permanent Live event per click. Current-room supporter rankings are derived from canonical, confirmed, ledger-backed tip, gift, and accepted paid-request events. Reversed or refunded value is excluded, and public identity follows the user's ranking privacy choice.

Live reports use the central Trust & Safety report taxonomy and queue. An authorised moderator participant-removal enforcement writes an audit event and a durable LiveKit `remove_participant` outbox intent. Moderation never edits financial history. Rejoining replaces the activity, goal, reaction, and supporter views from durable server state, while canonical financial-event uniqueness prevents duplicate recovery output.
# Release hardening update

- The real isolated LiveKit suite covers creator synthetic A/V publication over UDP, a subscribe-only public viewer, and a private 1:1 authorization/presence/reconnect/settlement journey.
- A 2-to-1 request snapshots its separate creator rate and has one requester/payer, one creator, and one named invited viewer. It becomes active only after all three named participants are present; it has one billable timer and one ledger settlement.
- Signed LiveKit events are persisted before state changes. Events arriving after a private session is ending, ended, or settled are persisted and deduplicated but are no-ops: neither joins nor leaves can reopen the lifecycle or alter settled billable seconds.
- Creator Studio exposes the existing server-authoritative tip-menu and goal commands. Goal resets advance a persisted contribution baseline, so confirmed historical contributions remain immutable while the new goal's progress starts at zero.
