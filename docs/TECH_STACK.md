# Technology Stack and Infrastructure Decisions

This document records the initial technology choices for the platform. It is authoritative for Phase 0 unless superseded by an explicit architecture decision record.

## 1. Architectural stance

Start as a **modular monolith** with strict domain boundaries. Keep media/streaming workers, background jobs and other high-throughput processes separately deployable, but do not fragment the business application into microservices prematurely.

The platform is expected to carry sensitive identity, paid content and complex financial state. Predictability, auditability and replaceable infrastructure providers take priority over novelty.

## 2. Repository layout

Use a monorepo:

```text
/
  AGENTS.md
  README.md
  docs/
  apps/
    web/
    api/
    worker/
  packages/
    ui/
    contracts/
  infra/
    docker/
    livekit/
    observability/
  scripts/
  tests/
```

`apps/api` remains the source of truth for domain rules. `apps/web` never becomes the authority for pricing, permissions, entitlements, commissions or financial state.

## 3. Frontend

### Choice

- Next.js
- React
- TypeScript in strict mode
- App Router
- Server Components where useful, Client Components only where interactivity requires them
- Native `fetch`/typed API client generated or maintained from the API contract

### UI

- Tailwind CSS for application styling
- A small first-party design system in `packages/ui`
- Accessible headless primitives where useful; do not allow a third-party component library to dictate business architecture
- Responsive web first; preserve the ability to introduce native apps later

### Forms and validation

- React Hook Form or equivalent focused form-state layer
- Zod may validate client-side payload shape, but server-side validation remains authoritative

### State

Avoid one global state store by default.

Use:
- URL/search params for navigational state
- server data/cache layer for API-backed state
- local React state for component interaction
- a dedicated client store only for genuinely cross-cutting ephemeral UI state

Never store authoritative wallet balances, entitlements, pricing or permissions only in client state.

## 4. Backend/API

### Choice

- Python
- FastAPI
- Pydantic models for API contracts and configuration
- SQLAlchemy 2 ORM/Core
- PostgreSQL driver compatible with async SQLAlchemy
- Alembic migrations

### API style

Primary application API: versioned REST/JSON.

```text
/api/v1/...
```

OpenAPI is generated from FastAPI and treated as a contract, not merely documentation.

WebSockets are used for realtime application events where needed. Streaming media itself is not transported through application WebSockets.

### Service boundaries

Use layers similar to:

```text
module/
  api/
  schemas/
  models/
  repositories/
  services/
  policies/
  events/
  tests/
```

Avoid generic `utils.py` dumping grounds and avoid controllers/routes containing complex business rules.

## 5. Database

### Choice

PostgreSQL is the system of record for relational/application state.

Use:
- explicit foreign keys and constraints
- UUID/UUIDv7-compatible identifiers where appropriate
- UTC timestamps
- exact/integer monetary representation
- explicit currency
- JSONB only where flexibility is genuinely useful and relational structure does not add value
- database transactions for multi-step state changes
- optimistic/pessimistic locking where required by financial/concurrency invariants

Do not begin with database-per-module or database-per-service patterns.

### Migrations

Alembic is mandatory. Autogenerated revisions must be reviewed and edited when necessary. CI should detect model/schema drift where practical.

## 6. Caching, ephemeral state and realtime coordination

### Choice

Redis.

Use Redis for:
- cache
- rate limiting primitives
- short-lived locks where a database lock is inappropriate
- websocket fan-out / transient realtime events
- presence/ephemeral room state where appropriate
- Celery broker/backend where selected

Use Redis Pub/Sub only for events that may be lost without violating correctness. Use a durable mechanism (database outbox, Redis Streams, queue, or persisted event record) for events that must survive restarts/retries.

PostgreSQL remains the truth for durable business state.

## 7. Background jobs

### Choice

Celery with Redis initially.

Worker classes should be separable by queue:

```text
default
media
email_notifications
moderation
analytics
financial_reconciliation
scheduled_content
```

Every retryable job that can create externally visible or financial effects must be idempotent.

Do not put CPU-heavy FFmpeg work inside API processes.

## 8. Object storage and media

### Interface

Use an S3-compatible storage abstraction.

Development may use a local S3-compatible service. Production provider selection must be validated against current acceptable-use rules, data residency needs, pricing and adult-content support before launch.

### Storage rules

- Buckets/objects private by default
- Never expose protected originals directly
- Generate purpose-specific derivatives
- Signed, short-lived access or a controlled delivery layer
- Separate original, preview, thumbnail and transcoded representations
- Store checksums/hash metadata
- Strip unsafe/unnecessary metadata when appropriate
- Design watermarking as an optional derivative pipeline

## 9. Media processing

### Choice

FFmpeg workers.

Responsibilities include:
- video probing
- transcoding
- thumbnail generation
- short PPV previews
- HLS generation where required
- audio normalization where appropriate
- safe derivative creation
- Story/video processing

Media processing state is persisted and retryable. Upload completion does not imply publish readiness.

## 10. Streaming architecture

### Initial choice: self-hosted LiveKit

Use LiveKit as the interactive realtime media layer.

Target use cases:
- public webcam rooms
- 1:1 private sessions
- 2-viewer-to-1-creator private sessions
- future multi-creator/collaboration rooms
- co-hosts and moderators
- realtime audio/video
- data channels for suitable ephemeral room events

### Why this shape

The business API owns room/session authorization, pricing, billing state, entitlements and moderation state. LiveKit is the media transport/SFU, not the owner of product truth.

### Components

```text
Web / Creator Studio
       |
       | application API / room token request
       v
FastAPI -------------------- PostgreSQL / Redis
       |
       | signed room grants
       v
LiveKit SFU <----> TURN
       |
       +---- Egress workers ----> S3-compatible storage / HLS / recordings
```

### Public vs private

For Phase 7, LiveKit may serve both interactive public rooms and private sessions.

Architect the playback abstraction so very large public broadcasts can later use a one-to-many HLS/LL-HLS delivery path while private/interacting participants remain on WebRTC. Do not hard-code UI/business state to a single transport.

### TURN

TURN/TLS support is mandatory for production reliability behind restrictive NAT/firewalls.

### Recording

Recording is policy-driven and must never be silently enabled. When recording is required/permitted, use separately deployed Egress and secure storage with explicit retention/moderation rules.

### Streaming billing invariant

Never compute paid private-session truth purely from browser timers. Server-authoritative session state records start/stop/heartbeat/reconnect events and feeds the financial system with idempotent usage events.

## 11. Realtime application events

FastAPI/WebSocket gateway + Redis may carry:
- notifications
- chat presence/events
- tip notifications
- session state
- moderation notices
- live goals/counters

Persisted chat messages, paid events, purchases, tips and moderation actions must be written durably before/alongside transient fan-out.

## 12. Search

Phase 0-9: PostgreSQL search capabilities are sufficient for basic exact/filter/query work.

Introduce OpenSearch only when justified by actual requirements such as:
- large-scale cross-domain full-text search
- complex ranking/faceting
- typo tolerance/analyzers beyond practical PostgreSQL use
- search-specific scaling requirements

Do not dual-write search indexes from request handlers. Use transactional outbox/events and asynchronous indexing.

## 13. Authentication and sessions

Implement account-centric auth in the API rather than delegating the platform's authorization model to a frontend library.

Baseline:
- secure password hashing
- email verification
- login throttling
- secure HTTP-only session/refresh-cookie strategy for web
- short-lived access credentials where tokens are needed
- refresh/session rotation and revocation
- device/session management
- password reset with single-use, expiring tokens
- MFA-ready architecture from Phase 0
- re-authentication hooks for high-risk actions

Roles and permissions are separate from authentication.

Creator/admin identity verification is a domain concern and must not be conflated with login authentication.

## 14. Authorization

Backend policy/service layer. Prefer capabilities/permission checks over role-name conditionals scattered throughout code.

Examples:

```text
creator.profile.edit
creator.content.publish
creator.messages.manage
creator.pricing.manage
group.creator.manage_profile
admin.moderation.review
admin.finance.view
```

Group delegation must resolve membership, accepted contract version and explicit permission grant.

## 15. Financial architecture

No payment provider is selected in Phase 0.

Create provider-neutral interfaces for:
- payment intent/charge
- refunds
- disputes/chargebacks
- payout destination
- payout request/status
- provider webhook ingestion

The immutable ledger remains provider-independent. Provider callbacks never directly mutate arbitrary wallet balances.

Before selecting a production processor, verify current support for the platform's business model, adult-content categories, countries, payout destinations, reserves/chargebacks and KYC requirements.

## 16. Email / notifications

Use provider adapters.

Domain creates notification intents/events; adapters deliver via:
- onsite
- email
- web push later
- mobile push later

Templates are versioned. Marketing and transactional preferences are distinct.

## 17. Observability

Use structured JSON logs and correlation IDs from Phase 0.

Adopt OpenTelemetry-compatible tracing/metrics architecture so API, workers and later streaming/media components can be correlated.

Minimum production observability:
- request/error rate
- latency
- DB pool health
- Redis health
- worker queue depth/failures
- webhook retries
- media processing failures
- streaming room/session metrics
- security/audit signals

Error-reporting vendor may be selected later behind environment/configuration boundaries.

## 18. Testing

Backend:
- pytest
- unit tests for domain services/policies
- integration tests against PostgreSQL/Redis
- migration tests
- API tests

Frontend:
- unit/component tests where useful
- Playwright for critical end-to-end flows

Critical financial/access invariants require backend integration tests.

## 19. Development environment

Docker Compose should provide local dependencies:

```text
postgres
redis
s3-compatible storage
livekit
turn (when practical for integration tests/dev)
api
worker
web
```

Developers may run web/API natively while dependencies remain containerized.

Provide `.env.example`; never commit secrets.

## 20. CI/CD

Initial CI should run:
- backend format/lint/type checks
- backend tests
- Alembic migration validation
- frontend lint/type checks
- frontend tests
- production builds
- dependency/security checks where practical

Do not automatically deploy migrations to production without controlled release sequencing.

## 21. Infrastructure progression

### Phase 0 / development

Docker Compose + CI.

### Early production

Containers on dedicated/cloud compute with managed or strongly operated PostgreSQL/Redis, private object storage and separately scalable workers/LiveKit nodes.

### Scale

Introduce an orchestrator (for example Kubernetes) only when operational/scale needs justify it. LiveKit/media processing can scale separately before the business API becomes microservices.

## 22. Provider abstraction rule

The following must use explicit provider interfaces/adapters:
- streaming control
- object storage
- CDN/delivery
- payments
- payouts
- email
- identity/KYC verification
- moderation vendors
- analytics/error reporting integrations

Domain entities must not store a provider-specific response blob as their only source of truth.

## 23. Initial decisions to avoid

Do not begin with:
- microservices
- GraphQL as the only API
- Kafka solely because the platform may become large
- Kubernetes in local development
- multiple primary databases
- blockchain/crypto accounting
- mutable wallet-balance-only accounting
- provider-specific business rules embedded across modules
- browser-authoritative live billing
- storing private media as public CDN URLs

## 24. Phase 0 pinned choices

For Phase 0, Codex should implement the following unless a concrete blocker is discovered and documented:

```text
Frontend:       Next.js + React + TypeScript
Backend:        FastAPI + Python
ORM:            SQLAlchemy 2
Database:       PostgreSQL
Migrations:     Alembic
Cache/broker:   Redis
Jobs:           Celery
Tests backend:  pytest
Tests e2e:      Playwright foundation
Styling:        Tailwind CSS
Observability:  structured logging + OpenTelemetry-ready instrumentation
Local runtime:  Docker Compose
Streaming dev:  LiveKit self-hosted configuration scaffold (not full product implementation)
Media tooling:  FFmpeg availability/scaffold (not full transcoding implementation)
```

Use current stable releases at repository initialization, never canary/beta versions unless explicitly approved, and commit lockfiles. Do not perform opportunistic major upgrades during unrelated feature work.
