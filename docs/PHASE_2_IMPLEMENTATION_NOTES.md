# FanBackstage Phase 2 implementation notes

Phase 2 separates private uploaded media from publishable content. `MediaAsset` owns an opaque, private storage key and processing lifecycle; `ContentItem` owns publication, access policy and creator ownership. Galleries keep explicit stable item positions, while standalone video content references one source asset. Neither public schemas nor browser routes expose source keys or permanent object URLs.

Creators request a short-lived, content-type-bound direct upload URL only after server-side approval checks. Finalization verifies object metadata and queues Celery processing. Image processing creates thumbnail, display and blurred-preview derivatives; video processing uses FFprobe/FFmpeg to create poster, preview-clip and playback derivatives. Creators select a video preview start/duration before review; the asynchronous worker replaces only the private preview derivative. A failed asset records its attempt count and can be requeued by its owner only while it remains below the configured retry bound. Row locking and unique derivative constraints make processing/recovery idempotent.

Content follows the enforced Phase 2 lifecycle: `draft -> processing -> pending_review -> published`, with `pending_review -> rejected` and published archival. Adding gallery media or creating a video enters `processing`; submission requires ready media and, for a video, a ready creator-selected preview derivative. Administrators/moderators have a deliberately small approval/rejection queue with audit events. The full reporting, cases, appeals, and broader moderation operations remain Phase 13.

The access resolver is authoritative and deny-by-default. Published free content is accessible publicly; owner and moderation roles are privileged; other policies require an active, currently valid `ContentEntitlement`. Changing a content policy never creates, deletes or rewrites entitlement history. Delivery endpoints authorize first and then redirect only to a short-lived derivative URL. Public preview delivery additionally requires published, ready, non-moderated content and the creator's configured preview selection.

Development uses private S3-compatible MinIO pinned to `RELEASE.2025-09-07T16-13-09Z`. Community MinIO does not implement the S3 BucketCORS API, so the Compose service configures `MINIO_API_CORS_ALLOW_ORIGIN` with the development and Playwright frontend origins. Application storage code only creates/checks the private bucket; it has no MinIO-specific CORS bootstrap. CORS permits browser PUT/preflight requests but does not make the bucket or source objects public. Production object-storage/CORS policy remains operator-managed.

Known Phase 2 limits: there is no subscription, payment, purchase or entitlement-grant workflow; non-free policies therefore deny until a future legitimate entitlement source exists. There is no adaptive streaming pipeline, full moderation dashboard, or content feed/story product.
